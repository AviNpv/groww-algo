## Executive verdict (historical)

**FAIL — not approved for production deployment in its current state.**

The architecture is largely sound: the agents are advisory-only, the model adapter is bounded and redacts errors, the deterministic rule engine is independent of model output, existing positions remain managed by the pre-existing deterministic engine, and no new dependencies were added. However, two explicit requirements are not fully met and one new high-risk configuration path exists:

1. **B-01 (High):** Strategy evolution has no reliable rollback target after the first promotion, although rollback is explicitly required.
2. **B-02 (High):** The model adapter will read *any* environment variable named in the writable strategy config and send it as a Bearer token to *any* configured URL. With the pre-existing unauthenticated `/api/config` write endpoint and wildcard CORS, this creates a broker-credential exfiltration path.
3. **B-03 (High/Medium):** The new state-changing intelligence endpoints (`evolution/run`, `promote`, `rollback`) are unauthenticated and reachable from any CORS origin.

After those are fixed, and with `require_for_entries: true` / `fail_closed: true` enforced, the layer should be re-reviewed for **PASS WITH CONDITIONS**.

**Status: PASS on core controls; HIGH exception B-02**

| Requirement | Evidence | Assessment |
|---|---|---|
| Reads only one configured env var | `model_adapter.py:107,121-131` — `os.environ.get(self._key_env)`, one name only. | PASS mechanically; see B-02 for the name being attacker-configurable. |
| Forces `allow_paid=false` | `config.py:66-70` and `model_adapter.py:98-99`; `ModelHealth.paid_allowed=False` at `model_adapter.py:373`. | PASS |
| No silent provider/model fallback | `model_adapter.py:103-118` selects exactly one `base_url`/`model`; `complete()` at `275-352` retries the same endpoint only. `/api/intelligence/health` (`api.py:170-181`) probes method names on one module, not alternative providers. | PASS |
| Bounded timeouts/retries/rate limit | `model_adapter.py:104-106` clamps timeout to 1–120 s and retries to 0–4; `67-88` sliding-window limiter; `154-167` caps response read at 1 MB; `248-260` caps backoff/Retry-After. | PASS. Note `rate_limit_per_minute <= 0` disables limiting (`model_adapter.py:76-77`); config is trusted-operator controlled. |
| Errors redacted | `model_adapter.py:57-64` caps to 300 chars and replaces the exact secret; `319-347` never echoes response bodies, headers, or `ValidationError` text; auth failures return only HTTP code (`321-328`). | PASS |
| Usage logged without secrets | `ModelUsage` (`models.py:132-144`) carries provider/model/tokens/timing/error/correlation only; saved at `model_adapter.py:209-242`; storage schema `storage.py:76-87`. | PASS |

**B-02 (High) — credential redirection via writable model config.** `api_key_env` and `base_url` come from the strategy YAML (`config.py:15,17`; shipped values `config/strategy.yaml:702,704`). The adapter forwards the named env var as `Authorization: Bearer ...` (`model_adapter.py:133-138`) to `base_url + "/chat/completions"` (`model_adapter.py:157-161`). The strategy YAML can be overwritten through the unauthenticated `PUT /api/config` (`engine/api.py:755-764`) with wildcard CORS (`engine/api.py:31-37`). An attacker can therefore set `api_key_env: GROWW_API_SECRET` (or the TOTP/access-token variable) and `base_url: https://attacker.example`, then invoke `/api/intelligence/health` or a scan with intelligence enabled, causing a broker secret to be sent off-host. This violates the intent of requirements 1–3 even though only "one configured variable" is read.

**Remediation for B-02:** allowlist `api_key_env` to a single non-broker variable (e.g. only `GROQ_API_KEY`), require HTTPS and an allowlisted host for `base_url`, reject intelligence model settings from the generic config editor, or move adapter settings into a protected file not writable via `/api/config`. Independently, authenticate/restrict the config API and tighten CORS.

## Requirement 4 — Agent capability boundaries and evolution promotion

**Status: FAIL on rollback; otherwise PASS**

### Agent boundaries — PASS
- No intelligence module imports or calls `broker.buy`/`sell`, `groww_auth`, or config writers other than the evolution module (grep over `engine/intelligence/*.py`).
- Risk/session/permission reads are deterministic: `rule_engine.py:99-121` reads `engine.enabled`, `autotrade`, `allow_new_entries`; `rule_engine.py:255-266` calls `strategy.can_open_new`; `rule_engine.py:161-184` floors score at 85 and R:R at 2.0; `rule_engine.py:268-287` checks duplicates/daily caps. None of these consume agent output.
- Model output fields that could influence identity/status are overwritten (`agents.py:120-129`).

### Promotion path — mostly PASS
- Allowed keys are exactly four deterministic numeric leaves (`evolution.py:33-38`): `exit.initial_stop_loss.atr_multiplier`, `exit.target.target_r_mult`, `exit.trailing_stop.activate_at_r`, `risk.minimum_risk_reward`.
- Candidate generation only applies fixed multipliers and validates each diff (`evolution.py:282-333`, `_assert_only_safe_changes` at `155-163`).
- Absolute safety is checked before promotion (`evolution.py:121-152`, called at `550`) and the main API validator is reused (`evolution.py:199-218`).
- Atomic write with lock, `.bak`, temp file, `os.replace`, and config reload (`evolution.py:221-235`); default file explicitly refused (`evolution.py:224-225`).
- Auto-promotion requires `auto_promote=true` plus recorded real shadow sessions (`evolution.py:565-603`, `486-524`); shipped config has `auto_promote: false` (`config/strategy.yaml:723`).

**B-01 (High) — rollback has no target after the first promotion.** `run_once()` takes the parent ID only from `store.active_version()` (`evolution.py:685-686`). If no active version has ever been recorded, the first promoted version has `parent_version_id = None`. Validated candidates are immediately moved to status `shadow` (`evolution.py:718-728`) and are not among the statuses considered by `rollback()` (`evolution.py:605-639` looks for a parent, then any status in `validated|active|rolled_back`). The `.bak` written by `_atomic_write_strategy` (`evolution.py:228-231`) has no API or code path to restore it. Consequently, a first promotion made through `POST /api/intelligence/strategy/{id}/promote` (`api.py:277-293`) or auto-promotion cannot be rolled back via `POST /api/intelligence/strategy/rollback` (`api.py:296-306`); it returns `no_target`. This fails the explicit rollback requirement.

**Remediation for B-01:** seed a `validated`/baseline version from the current `strategy.yaml` before the first promotion; keep the previous active version in a rollback-eligible status; or add an authenticated rollback that restores `.bak` under `_WRITE_LOCK`, re-runs `_validate_yaml_for_write` + `_check_absolute_safety`, and reloads config. Add a regression test covering "promote with empty version store → rollback succeeds".

**F-05 (Medium) — defense-in-depth gap in write validation.** `_atomic_write_strategy` calls `_validate_yaml_for_write()` (`evolution.py:226`), but when `engine.api._validate_strategy` is importable that function returns after the generic validator (`evolution.py:202-211`) and *does not* call `_check_absolute_safety()`. `promote()` currently compensates by calling `_check_absolute_safety()` at `evolution.py:550`, and `rollback()` goes through `promote()`. Still, any future direct caller of `_atomic_write_strategy` could write a document with a lowered score/R:R floor. **Remediation:** call `_check_absolute_safety()` inside `_atomic_write_strategy` after parsing, not only at call sites.

**F-09 (Low) — inert safe key.** `evolution.py:65-67` documents that `risk.minimum_risk_reward` is behaviourally inert because live code reads `entry.risk.minimum_risk_reward`/`entry.min_risk_reward`. This is an effectiveness issue, not a security bypass; document in operator notes or remove from `SAFE_PATHS`.

**B-03 (High/Medium) — unauthenticated intelligence lifecycle API.** `api.py:272-306` exposes `POST /evolution/run`, `POST /strategy/{version_id}/promote`, and `POST /strategy/rollback` with no authentication/CSRF, included into the main app at `engine/api.py:40`, whose CORS allows all origins with credentials (`engine/api.py:31-37`). A remote page can trigger research and promotion of a validated version (changes are constrained to the four safe keys, but active config is still rewritten). **Remediation:** require auth/CSRF or bind the API to localhost; at minimum, gate these three routes behind an explicit operator token.

## Requirement 5 — Deterministic rule engine and fail-closed behavior

**Status: PASS with one condition**

- `engine/intelligence/rule_engine.py:45-305` is pure deterministic evaluation: market session/permissions (`99-121`), freshness (`123-147`), deterministic entry action (`149-158`), score/confirmations/status (`160-181`), stop/target/R:R (`183-200`), position sizing (`202-217`), exposure (`219-253`), portfolio/daily-loss (`255-266`), duplicates (`268-287`). `allowed = all(check.ok ...)` at `293`. No model call and no order call.
- `engine/intelligence/orchestrator.py:301-305` requires **all** of `rules.allowed`, `debate.decision == approve_candidate`, `model_ok`, no unresolved critical objections, and no flagged reports. Agent output alone cannot produce `ALLOW`.
- Missing/degraded model data fails closed: `agents.py:26-66` returns an error report with a critical objection and `abstain`; `debate.py:102-106,131-142` marks insufficient evidence/rejects; `orchestrator.py:273-305` accumulates reject reasons and refuses `ALLOW`.
- Existing positions are untouched by the gate: `engine/engine.py:147-148` calls `manage_positions(now)` before scanning; `_intelligence_gate` appears only at `engine/engine.py:217` immediately before `broker.buy`.
- Exceptions in the orchestrator reject by default: `orchestrator.py:323-332` with `_require_for_entries()` defaulting true (`orchestrator.py:370-374`, `config.py:10`, `config/strategy.yaml:696`).

**F-04 (Medium, condition) — explicit fail-open branch.** `orchestrator.py:333-339` returns `ALLOW` on an orchestrator exception when `require_for_entries` is false, without rules or debate. This is documented as operator-controlled, not a silent fallback, but it is a bypass if that flag is changed. Shipped config sets it true. **Remediation:** keep `require_for_entries: true` in production; preferably remove the `ALLOW` branch and replace it with a distinct "intelligence disabled — no AI-dependent entries" mode.

**Note:** the `fail_closed` flag itself (`orchestrator.py:296-305`) is currently redundant in the normal path: `allowed` already requires the same conditions. Turning it off does not create a bypass; no finding.

## Requirement 9 — Prompt injection from market text

**Status: CONDITIONAL — mitigated for execution safety, not fully sanitized at the input boundary**

**Sources of untrusted text in the payload:**
- `snapshot.py:150` copies `FeedState.message` from `marketdata.health()`; `marketdata.py:75,81,87-89` may include upstream error text.
- `snapshot.py:245-250,263-264,279` copies `reasons`, `patterns`, `status`, and `rejection_reasons` from scan/build-entry results. `scoring.py:266-268` builds reasons mostly from fixed templates plus `patterns` names/notes; `snapshot.py:223` can add raw exception text.
- `prompts._sanitize()` (`prompts.py:147-168`) filters key *names* but does not fence, escape, or length-cap string *values*.

**Mitigations that are present:**
- Strong system-prompt rules: cite only supplied refs, list gaps, no fabrication, out-of-scope topics forbidden (`prompts.py:31-48`); explicit JSON output contract (`prompts.py:50-62`).
- Data is placed in a separate `user` JSON payload, not in the system prompt (`model_adapter.py:140-152`).
- Evidence refs are restricted to refs actually present in that payload; unsupported refs are dropped and recorded (`agents.py:132-155`).
- Runtime-owned fields (identity, symbol, snapshot ID, timestamp, status, model, usage ID) are overwritten (`agents.py:120-129`), so injected text cannot forge a trusted agent role.
- **Most importantly, model output has no execution capability.** Final `ALLOW` requires deterministic rules plus a separately computed debate verdict and all reports OK (`orchestrator.py:301-305`); the rule engine never reads agent output (`rule_engine.py:45-305`); the gate only blocks/permits a pre-existing paper buy (`engine/engine.py:217-228`); exits are unaffected (`engine/engine.py:147-148`).

**F-08 (Medium, residual) — advisory-level injection remains possible.** An upstream error string containing instruction-like text could bias an agent's `recommendation`/`objections`, potentially causing nuisance rejections or an over-optimistic debate consensus, though it cannot place orders or bypass deterministic rules. **Remediation:** wrap all untrusted string values in explicit delimiters (e.g. `<untrusted_market_text>...</untrusted_market_text>`), cap their length before prompt construction, strip/escape instruction-like control sequences, and downgrade a report to `insufficient_data` when a material share of its evidence refs are dropped by `_validate_refs`.

## Blocking issues that must be fixed before production deployment

1. **B-01 — Implement a real rollback path.** Seed a baseline version before the first promotion and/or restore the validated `.bak` under lock with revalidation and config reload. Add a regression test for "first promotion → rollback". Evidence: `engine/intelligence/evolution.py:221-235,526-563,605-639,685-728`; `engine/intelligence/api.py:277-306`.
2. **B-02 — Remove the credential-redirection path.** Allowlist `api_key_env` to a non-broker model key and `base_url` to HTTPS allowlisted hosts; keep these settings out of the generic writable config surface. Evidence: `engine/intelligence/config.py:15,17`; `engine/intelligence/model_adapter.py:107,109-117,121-138,157-161`; `engine/api.py:31-37,755-764`.
3. **B-03 — Protect the state-changing intelligence API.** Add authentication/CSRF or enforce localhost-only access for `/api/intelligence/evolution/run`, `/promote`, and `/rollback`; tighten CORS. Evidence: `engine/intelligence/api.py:272-306`; `engine/api.py:31-40`.
4. **Configuration condition (F-04):** production config must retain `enabled` only when intentionally deployed, `require_for_entries: true`, `fail_closed: true`, `auto_promote: false` unless shadow promotion is deliberately commissioned, and `allow_paid: false`. Evidence: `config/strategy.yaml:691-740`; `engine/intelligence/orchestrator.py:323-339`.

## Final verdict

**FAIL.**

The intelligence layer does not introduce real order placement, does not expose secrets into agent prompts by design, uses a bounded and redacting model adapter, keeps deterministic rules authoritative, and adds no dependencies. Those controls are acceptable. However, the evolution rollback requirement is not satisfied, and the combination of writable model-endpoint/key-name config with an unauthenticated, wildcard-CORS API creates a credible path for broker-credential exfiltration and unauthorised strategy promotion. These are production-blocking. Remediate B-01/B-02/B-03, enforce the configuration conditions, and re-audit for a PASS/Pass-with-conditions sign-off. No deployment or commit was performed as part of this review.

1. The pre-existing `allow_origins=["*"]` + `allow_credentials=True` CORS (`engine/api.py:31-37`) and unauthenticated `PUT /api/config` (`:771-780`) still exist. 2. `INTELLIGENCE_ADMIN_TOKEN` must be set to a strong value in production; while unset, all three mutation routes correctly return 503.
3. Keep `intelligence.enabled: false` unless the advisory layer is deliberately commissioned; keep `require_for_entries: true`, `fail_closed: true`, `auto_promote: false`, `allow_paid: false` (current `config/strategy.yaml:691-723` satisfies these). `research_enabled: true` is currently inert while `enabled: false`; if enabled, research remains bounded to the four safe YAML leaves and real shadow evidence.
4. `GROQ_API_KEY` / `INTELLIGENCE_MODEL_API_KEY` must be model-only credentials; they are the only env names the adapter may read, and requests go only to allowlisted HTTPS hosts or a localhost endpoint without a Bearer header.
5. Low-severity, unchanged advisory surfaces: raw upstream market/error text can still bias model reports (prompt injection cannot place orders), and `urlopen` follows redirects from the allowlisted trusted hosts. Neither creates a promotion, rollback or credential bypass.

### Mode-switch addendum (2026-11-22)

A new `POST /api/intelligence/mode` endpoint serves the dashboard Normal/AI
switch. Security review of the current implementation:

- It changes exactly one boolean (`intelligence.enabled`) in both strategy YAML
  files. `_set_scalar()` preserves all other content and `_validate_strategy()`
  performs the full safety validation before either file is written. Tests prove
  no other YAML value changes.
- It cannot change `app.mode`, execution mode, live-order flags, safety kill
  switches, capital, risk, exposure limits, model credentials, `base_url` or
  `api_key_env`. Those remain covered by the existing absolute and write-time
  validators.
- When `INTELLIGENCE_ADMIN_TOKEN` is configured, the endpoint calls the same
  constant-time `_require_admin()` gate as evolution/promote/rollback. When it is
  unset (the current Render state), the switch is open, matching the pre-existing
  unauthenticated Settings editor. This is an operator UI function, not an agent
  capability; network access must still be restricted to trusted operators.
- Enabling AI does not bypass fail-closed behavior: missing model health or an
  orchestration/rule/debate failure rejects new entries. Disabling AI restores
  the original deterministic path immediately.
